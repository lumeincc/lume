# Releasing

A release is a tag. Pushing `v*` builds an APK, verifies it is signed, and opens
a **draft** release — a person decides when it goes public.

```bash
git tag v0.1.1 && git push origin v0.1.1
```

## First, once: the signing key

Android will not install an unsigned APK. Not "with a warning" — the installer
refuses it. Every release published before this was set up was undownloadable in
practice for that reason.

Signing an Android app costs nothing and needs no certificate authority. You
generate the key yourself, and Android accepts it. The only thing that matters is
that **you keep it**: the key is the app's identity to every device that has
installed it, and losing it means existing users cannot receive an update — they
have to uninstall and reinstall, losing local data. There is no recovery.

### 1. Generate the keystore

Run this yourself. Choose a strong password when prompted, and store it in your
password manager — nobody else should ever type it, including any tooling.

```bash
keytool -genkeypair -v -keystore lume-release.jks -alias lume -keyalg RSA -keysize 4096 -validity 10000
```

`-validity 10000` is about 27 years. An expired signing key cannot sign updates,
so a short validity is a slow-motion outage.

`keytool` asks for a name and organisation. Whatever you enter is embedded in the
certificate and visible in the APK — for a messenger that asks users for no
identity, consider what belongs there.

### 2. Back it up before doing anything else

Two copies, offline, not on the machine that builds. If this file is lost, the
app cannot be updated again.

### 3. Put it in the repository secrets

```bash
base64 -w0 lume-release.jks > keystore.b64
```

Then in **Settings → Secrets and variables → Actions**, add four secrets:

| Secret | Value |
|---|---|
| `ANDROID_KEYSTORE_BASE64` | the contents of `keystore.b64` |
| `ANDROID_KEYSTORE_PASSWORD` | the keystore password |
| `ANDROID_KEY_ALIAS` | `lume` |
| `ANDROID_KEY_PASSWORD` | the key password (the same one, unless you set two) |

Delete `keystore.b64` afterwards. Keep the `.jks`.

## How signing is wired

`android/` is generated by `expo prebuild` on every build and is not in the
repository, so a signing config cannot simply be committed — it has to be
re-applied each time. That is what
[`plugins/with-release-signing.js`](plugins/with-release-signing.js) does: during
prebuild it points the release build type at a real signing config whose values
Gradle reads from the environment. No password is ever written into a file.

The workflow fails early and loudly in three places, because the failure this
replaces was silent:

1. **Before building**, if a tagged release has no keystore secret.
2. **After prebuild**, if the signing config was not actually applied — the Expo
   template can change, and a template change must not degrade quietly into a
   debug-signed build.
3. **After building**, by asking `apksigner` whether the APK is really signed
   rather than trusting that the previous steps worked.

A manual run (`workflow_dispatch`) with no keystore still builds, stays
debug-signed, and is named `-unsigned`. That is for testing the workflow itself
without spending a version number, and it is never published.

## What this does not give you

- **Play Store distribution.** That needs an app bundle, a developer account
  (one-off fee), and an identity on file with Google.
- **Reproducible builds.** The published checksum proves the file you downloaded
  matches the file CI produced. It does not prove CI built it from this source.
- **Escape from the "unknown sources" warning.** Any APK installed outside the
  Play Store shows it. Signing does not remove it, and nothing except Play
  distribution does.
